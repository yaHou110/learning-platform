# ADR-0004: Database — PostgreSQL 16 + Drizzle ORM (no vector DB in v1)

- **Status:** Accepted
- **Date:** 2026-07-11
- **Deciders:** founder (Mavis orchestrator, founder authorization in chat 2026-07-11)

---

## Context

v1 needs a primary data store for:

- Multi-tenant application data (tenants, users, roles, courses, lessons, enrollments, progress, audit log) — see `BOUNDED_CONTEXTS.md`.
- A server-side session store for the auth model (ADR-0005).
- JSON-shaped plugin-defined metadata, where the schema is owned by individual plugins (ADR-0006) and must not break the core schema when it changes.
- A durable, self-hostable database engine that fits on a single 4 GB VPS (`ARCHITECTURE_CONSTRAINTS.md` C1) and is license-clean (no GPL in core).
- A query layer that is TypeScript-native so the plugin-typing story in ADR-0006 stays strong.

AI features (summarization, transcription, recommendation) are explicitly **out of scope for v1** per `MVP_SCOPE.md` — so a separate vector database is not needed in v1.

## Decision

We adopt **PostgreSQL 16** as the primary database, with **Drizzle ORM** as the query layer. **No vector database in v1.**

Specifically:

- Engine: **PostgreSQL 16** (single instance, single primary; read replicas deferred to a later ADR if needed).
- ORM: **Drizzle ORM** (`drizzle-orm` + `drizzle-kit` for migrations), with TypeScript-strict schema definitions.
- Migrations: SQL files generated by `drizzle-kit` and applied through a small `pnpm db:migrate` script. No ORM-level "auto-sync to schema" in any environment.
- Multi-tenant isolation: a `tenant_id` column on every tenant-scoped table, plus **PostgreSQL Row-Level Security (RLS)** as a second layer of defense. The exact policy table and the RLS helper function are defined in implementation, not in this ADR; the *contract* — "every query goes through a tenant-scoped Drizzle client that sets `app.tenant_id` for the connection" — is fixed here.
- Plugin-defined metadata: stored as **`jsonb` columns** with a Zod-validated shape, validated at the application boundary, not by the database.
- Connection pooling: **`pg` Pool** in the Next.js server runtime, sized to VPS RAM budget.
- Backups: logical dumps via `pg_dump` on a daily cron, plus WAL archiving (deferred detail to deployment ADR).

## Rationale

- **Postgres** is self-hostable, license-clean, has mature RLS for multi-tenant (C2), handles JSONB cleanly, and runs well on a small VPS. It is the obvious choice given the constraints.
- **Drizzle** is TypeScript-native, has a small runtime, supports the `jsonb` shape we need for plugin metadata, and produces typed queries that match the plugin-typing story in ADR-0006. It does not require a separate codegen service or a heavy runtime.
- **RLS** gives us a second line of defense on top of application-level `tenant_id` filtering — exactly what `ARCHITECTURE_CONSTRAINTS.md` C2 asks for ("data isolation is enforced at more than one layer").
- **No vector DB in v1** matches `MVP_SCOPE.md` (AI features are out of scope) and `ARCHITECTURE_CONSTRAINTS.md` supporting constraints (no GPU dependency). When AI features land, the *addition* of a vector store is its own ADR; nothing in this ADR blocks that.

### Alternatives considered

| Option | Verdict | Why |
| --- | --- | --- |
| **MySQL 8** | Rejected | Weaker JSONB ergonomics, no first-class RLS, multi-tenant story is more manual. |
| **SQLite (single file)** | Rejected | Multi-tenant write contention on a single VPS with 3+ active tenants; not designed for our concurrency target. |
| **Prisma** | Rejected (for v1) | Heavier runtime (~20 MB), separate schema DSL, codegen step. Drizzle gives us the same TypeScript story with less moving parts. Re-evaluate only if Drizzle blocks us. |
| **Supabase** | Rejected | Proprietary BaaS as the primary store violates `ARCHITECTURE_CONSTRAINTS.md` C3. |
| **MongoDB** | Rejected | License + pedagogy mismatch; relational data (users ↔ enrollments ↔ progress ↔ audit) is the bulk of v1. |
| **Postgres + a separate vector DB (pgvector / Qdrant / Weaviate)** | Deferred | Out of scope for v1. pgvector is the natural add-on *inside Postgres* when AI features land; no separate service needed. |

## Consequences

### Positive

- One engine to operate, one backup story, one connection pool to size.
- Strong typing end-to-end (DB schema → query → plugin manifest).
- RLS gives a second isolation layer on top of application filtering.
- `jsonb` lets plugins evolve their metadata without core migrations.

### Negative

- Drizzle's tooling is younger than Prisma's; some advanced cases (e.g. complex lateral joins) require raw SQL. We accept this.
- RLS policies must be maintained alongside the schema; we mitigate by colocating the policy SQL with the table DDL in the migration files.
- A single Postgres instance is a single point of failure in v1. We accept this for v1; the `99.5%` SLO in `ARCHITECTURE_CONSTRAINTS.md` is achievable with a single primary + daily backups.

### Neutral

- We deliberately do **not** commit to a specific Postgres hosting (VPS vs managed) in this ADR — that is Q5 in `PROJECT_STATE.md`.

## When to revisit

- When AI features enter scope (a new ADR will add pgvector or a dedicated vector store).
- When a single primary becomes a measured bottleneck (read replicas, partitioning).
- If Drizzle blocks us on a specific query pattern we cannot express in a maintainable way.
- When the schema-free needs of plugins outgrow `jsonb` validation and we need typed columns per plugin (likely a v1.2 problem).

A new ADR is required to overturn this one.
